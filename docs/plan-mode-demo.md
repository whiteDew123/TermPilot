# Plan 模式课堂演示方案

面向同学的 15 分钟演示，目标是让人看懂三件事：

1. **规划和执行是分开的**：规划阶段没有工具，模型只能"想"，不会偷偷改文件。
2. **计划是数据，不是一段话**：任务 id、依赖、环检测都要过校验，坏计划不会往下跑。
3. **人是最后一道闸门**：执行前可以展开看全图、补充要求改计划、直接取消。

---

## 二、准备一个演示沙盒

不要拿 TermPilot 仓库本身演示：文件多、读得慢、改坏了心疼。新建一个 3 文件的小站点：

```bash
mkdir -p demo-plan
cd demo-plan
git init && git add . && git commit -m "demo baseline" --allow-empty
```

`demo-plan/index.html`：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>Demo Site</title>
  <link rel="stylesheet" href="styles.css">
</head>
<body>
  <nav>
    <a href="index.html">首页</a>
  </nav>
  <main>
    <h1>Demo Site</h1>
    <p>这是一个用于演示 Plan 模式的静态站点。</p>
  </main>
```

`demo-plan/styles.css`：

```css
body { font-family: system-ui, sans-serif; max-width: 720px; margin: 40px auto; }

```

`demo-plan/README.md`：

```markdown
# Demo Site

```

提交一次基线，演示结束后可以直接 `git checkout .` 还原。

## 三、15 分钟分镜脚本

### 0:00–1:30 开场：先制造问题

**操作**：正常启动 TermPilot，输入 `/mode` 看当前模式。

**讲解**：

> 默认是 ReAct，边想边做。简单任务很爽，但复杂任务有两个问题：一是你事前不知道它要干什么，二是它可能改到一半你才发现方向不对。Plan 模式就是把"想"和"做"拆开：先给你一张施工图，你签字，它才动工。

**可选对比**：先用普通输入跑一个 20 秒的小任务，让同学看到 ReAct 直接调工具、没有确认环节。再切 Plan。

### 1:30–2:30 入口：三种进法

**操作**（任选一种，建议讲全三种）：

```text
/plan                    # 只有下一条任务走 Plan，执行完回到原模式
/plan <任务>             # 这一条直接走 Plan
/mode plan               # 或 Shift+Tab 切到 plan 会话模式，之后每条输入都先规划
```

**讲解**：

> `/plan` 不带参数是"一次性"的，适合临时来一发；`/mode plan` 是会话级的，适合整节课都在做规划型任务。演示里用 `/plan <任务>` 最直观。

### 2:30–4:00 规划：模型这时没有工具

**操作**：输入主演示任务（见第四节）。

**屏幕预期**：先出现规划中的提示，然后弹出折叠的计划摘要，包含目标、任务数、并行批次数、当前可执行数、首批和最终收敛任务。

**讲解**：

> 注意，规划阶段工具是关闭的，提示词里也不列工具清单。它现在只能输出一份 JSON 计划，读文件、写文件这些动作必须写进计划，等我们审完才执行。如果模型忍不住返回工具调用，TermPilot 会明确提示"工具调用未执行"，不会把调用文字当计划。

**现场验证**（很有说服力）：

> 现在规划已经结束了，我们看 `git status`——工作区还是干净的。它一行代码都没动。

### 4:00–6:00 审阅：这是 Plan 模式的核心

**操作 1**：按 `Ctrl+O` 展开完整计划。

**屏幕预期**：出现带边框的计划表，每行有任务 id、状态图标、类型、依赖和描述；底部显示进度和状态。

**讲解**：

> 默认折叠是为了不刷屏，展开后能看到完整 DAG。每个任务有 id、类型和依赖。类型大致分读、写、分析、验证这几类；依赖决定谁先跑。

**操作 2**：按 `I`，输入一条补充要求，例如：

```text
不要新建 contact.html，只做 about.html；最后一步用 grep 检查导航链接，不要用浏览器。
```

**屏幕预期**：提示"已收到补充要求，正在修改计划..."，然后重新弹出计划摘要，再进一次审阅。

**讲解**：

> 这就是"人审"的价值。不用取消重来，直接在当前计划上提要求，模型改完再给你看一遍。改计划本身也要重新过一遍 JSON 校验。

**按键速查**（建议写在黑板或副屏）：

| 按键 | 作用 |
| --- | --- |
| `Enter` | 按当前计划执行 |
| `Ctrl+O` | 展开 / 收起完整计划 |
| `ESC` | 展开时先折叠；再按取消本次计划 |
| `I` | 输入补充要求，改完再审一次 |
| `/view` | 终端读不到单键时的行输入兜底，展开完整计划 |
| `/cancel` | 执行中取消 |

> 注意：`ESC` 在展开状态下第一次只折叠，不会直接取消；方向键也不会误触取消。

### 6:00–9:00 执行：看批次，不要只看结果

**操作**：按 `Enter` 执行。

**屏幕预期**（按批次出现）：

```text
🚀 开始执行计划...
▶️ 执行任务 [T1]: 读取 index.html 和 styles.css
✅ 完成 [T1]
⚡ 本轮并行执行 2 个任务: T2, T3
▶️ 并行任务 [T2]: 新建 about.html
▶️ 并行任务 [T3]: 更新 index.html 导航
✅ 完成 [T2]
✅ 完成 [T3]
▶️ 执行任务 [T4]: 检查链接和标题
✅ 完成 [T4]
```

**讲解**：

> 调度是分轮的：每一轮把所有"依赖已经完成"的任务拿出来一起跑。T2 和 T3 互不依赖，所以同批并行；T4 依赖它们，只能等下一轮。并行上限是 4 个线程。
>
> 还有一条约束写在规划提示词里：会写同一个文件的任务不能同批，必须让后一个依赖前一个，否则两个线程同时改一个文件会丢修改。
>
> 每个任务有独立上下文，上游任务的结果会按依赖注入下游。所以 T4 不需要重新读一遍所有文件，它拿得到 T2、T3 的结果。

**可选演示**：执行中按 `ESC` 或输入 `/cancel`，展示"已取消当前计划执行"，并说明已完成的不会回滚、未开始的会标成 SKIPPED。

### 9:00–11:00 验收：让结果可检查

**操作**：

```bash
cd demo-plan
git diff
ls
```

**讲解**：

> 演示不要停在"模型说完成了"。看 diff：改了哪些文件、导航有没有真的加上、about.html 是否存在。Plan 的最后一个任务通常就是验证，但人还是要自己看一眼。

**回滚兜底**：

```text
/snapshot          # 查看当前项目的 pre-turn / post-turn 快照
/restore 1         # 恢复到最近一次任务开始前
```

或者直接 `git checkout .`。

### 11:00–13:00 对比：什么时候不该用 Plan

**操作**：切回 ReAct，输入同一个需求（不带 `/plan`），让同学看差异。

**对比表**（可直接投屏）：

| 维度 | ReAct | Plan-and-Execute |
| --- | --- | --- |
| 执行前能否看到步骤 | 不能 | 能，还能改 |
| 模型调用次数 | 由 Action 轮数决定 | 多一次规划，每个任务至少一次 |
| 适合的任务 | 简单、探索型、边看边决定 | 步骤多、依赖明确、需要事前 review |
| 失败后的处理 | 模型自己调整 | 完成度低于一半会重规划（默认最多 2 次），否则下游标 SKIPPED |
| 并行 | 同一轮多个只读工具可并行 | 独立任务按批次并行 |

**讲解**：

> Plan 不是"更高级的 ReAct"，它是用一次额外的规划调用换确定性和可审阅性。一步就能完成的任务，规划器会按提示词要求给最短计划，不会硬凑步骤——但你还是多付了一次规划请求。所以简单任务、强交互调试、时间很紧的时候，用 ReAct 更合适。

### 13:00–15:00 收尾：三个设计取舍

> 1. **规划器不给工具**：不是能力缺失，是故意让它"只说不做"，避免规划阶段产生副作用。
> 2. **计划严格校验**：id 重复、依赖不存在、有环，任何一项不合格直接失败，不自动重试、不悄悄退回 ReAct。宁可报错，也不带着坏计划执行。
> 3. **失败不静默**：下游任务会明确标成 SKIPPED，最终结果里列出哪些没做，不会假装全部完成。

**Q&A 预留问题**：

- 计划生成错了怎么办？→ 按 `I` 改，或 `ESC` 取消重来。
- 能不能中途改计划？→ 执行阶段不行，执行前可以；执行中只能取消。
- 并行会不会写冲突？→ 规划提示词约束同一文件必须串行；执行器按依赖批次调度。
- 为什么还要人审，不能全自动？→ 审阅是安全闸门，尤其是写操作；全自动可以去掉 review handler，但不建议在真实仓库这么做。

## 四、主演示任务（直接复制）

```text
/plan 在 demo-plan 目录完成一个小型静态站点：先读取现有的 index.html 和 styles.css，了解结构和样式；然后新建 about.html 页面，复用现有样式；接着更新 index.html 的导航，加上 about.html 的链接；最后用 grep 检查三个 HTML 文件的导航链接和标题是否一致。
```

预期计划形状（不保证逐字一致，但批次结构应该类似）：

| 任务 | 类型 | 依赖 | 说明 |
| --- | --- | --- | --- |
| T1 | FILE_READ / ANALYSIS | 无 | 读 index.html、styles.css |
| T2 | FILE_WRITE | T1 | 新建 about.html |
| T3 | FILE_WRITE | T1 | 更新 index.html 导航 |
| T4 | VERIFICATION | T2, T3 | grep 检查链接和标题 |

批次：`T1` → `T2, T3` 并行 → `T4`。

如果模型把"读 index.html"和"读 styles.css"拆成两个任务，更好：正好展示第一批就并行。

### 备用任务：证明"一步任务不硬凑"

```text
/plan 列出 demo-plan 目录的文件，并说明每个文件的职责
```

预期只有一个任务。用来回答"Plan 是不是什么都要拆成五步"。

### 对比任务：ReAct 版本

```text
在 demo-plan 里加一个 about.html，并更新首页导航
```

不加 `/plan`，直接回车。让同学观察：没有计划确认，直接开始调工具。

## 五、翻车预案

| 现场情况 | 处理 |
| --- | --- |
| 模型很慢，规划迟迟不出 | 提前录屏顶上；说明这是模型侧延迟，不是模式问题；换 flash 模型重试 |
| 计划拆得太碎或太粗 | 正好按 `I` 提要求："合并 T2 和 T3""把验证拆成独立任务"，现场演示改计划 |
| 计划 JSON 解析失败 | 直接报错是设计行为（不退回 ReAct）。念出错误原因，`ESC` 取消后重试一次；仍失败就切备用任务 |
| `Ctrl+O` 没反应 | 可能被终端/tmux 占用。改用行输入兜底的 `/view`；或提前换终端 |
| `I` 按了没反应 | 输入法没切英文；或终端不支持单键，改用行输入模式输入补充要求 |
| `ESC` 按一次没取消 | 当前处于展开状态，第一次只是折叠，再按一次才取消 |
| 执行写坏了文件 | `git checkout .`，或 `/snapshot` + `/restore 1` |
| 演示中途想停 | `/cancel`；已完成的保留，未开始的标 SKIPPED |
| 投屏暴露 Key | 不要打开 `.env`；启动前确认终端历史里没有 `export ...KEY=...` |

## 六、5 分钟极简版

时间不够时只保留这条主线：

1. （30 秒）`/mode` 看默认 ReAct，讲"边想边做 vs 先规划再执行"。
2. （1 分钟）输入 `/plan` 主任务，等计划出来。
3. （1 分钟）`Ctrl+O` 展开，指着依赖列讲 DAG 和并行批次。
4. （30 秒）按 `I` 提一条补充要求，展示计划被修改。
5. （1.5 分钟）`Enter` 执行，只讲"⚡ 本轮并行执行"和"✅ 完成"两类输出。
6. （30 秒）`git diff` 验收，收尾一句："Plan 用一次额外规划，换执行前的确定性和可审阅性。"
